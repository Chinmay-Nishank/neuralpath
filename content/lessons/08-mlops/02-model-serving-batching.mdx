## Intuition: Training Optimizes Throughput; Serving Battles Latency & Memory

During training, you batch 1,000 fixed-length sequences together offline. In production serving, requests arrive unpredictably at random times with lengths ranging from 20 tokens to 16,000 tokens!

Two serving patterns unlock production performance:
1. **ONNX Runtime (Classical & Vision):** strips Python framework overhead into fused C++/CUDA kernels—even running right inside browsers via WebAssembly/WebGPU.
2. **Continuous Batching & PagedAttention (vLLM / SGLang for LLMs):** instead of waiting for the longest sequence in a static batch to finish before starting new requests, **continuous batching** swaps finished requests out on *every single decode step*, while **PagedAttention** stores KV caches in non-contiguous memory pages like OS virtual RAM—eliminating memory fragmentation!

<Viz type="quantization" />

<Callout type="math-deep-dive" title="LLM Serving Latency Decomposition">
  - **TTFT (Time To First Token):** dominated by the compute-bound **prefill** pass over prompt tokens.
  - **ITL / TPOT (Inter-Token Latency):** dominated by **memory bandwidth** loading weights + KV cache once per generated token. Moving a 14 GB FP16 7B model across 1 TB/s memory takes at least ~14 ms per token (~70 tok/s theoretical ceiling at batch 1).
</Callout>
